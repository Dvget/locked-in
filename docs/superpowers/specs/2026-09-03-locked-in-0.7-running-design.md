# LOCKED IN 0.7 Running Mode Design

## Goal

Version 0.7 adds a native iPhone running mode to the existing LOCKED IN app while preserving the current strength, Polar, steps, weight, statistics, backup, and weekly-reporting features. Native runs and Polar runs remain separate records during the comparison phase.

## Version and scope

- Marketing version: `0.7.0`
- Build number: `27`
- Minimum platform remains iOS 17.
- The Cloudflare Worker and Polar OAuth implementation are not changed.
- Polar import remains active as a temporary benchmark.
- The native mode records outdoor runs with the iPhone through Core Location.
- Heart-rate recording is not part of this build, but the stored run format remains extensible.

## Dashboard simplification

- The top action card contains the single label `Training starten`; its current strength-only subtitle is removed.
- The weekly step average keeps its numeric value and removes the redundant suffix `Schritte`.
- The bottom weight card contains only `Gewicht`; its explanatory subtitle is removed.
- The existing dark LOCKED IN visual language, spacing, rounded cards, typography, and green accent remain unchanged.

## Training type selection

Tapping `Training starten` presents a full-screen custom LOCKED IN selection screen instead of a standard iOS action sheet.

The screen uses the visual structure of the existing strength-plan screen:

- LOCKED IN branding at the top.
- Two large full-width cards: `Krafttraining` and `Running`.
- Each card has a distinctive icon, concise description, and selected-state border/accent.
- A fixed green bottom button continues with the selected mode.
- `Krafttraining` opens the existing exercise selection without changing its behavior.
- `Running` opens a pre-run screen that shows GPS readiness and the location permission state.
- The actual recording starts only after the user presses the prominent start button and a short three-second countdown completes.

If an unfinished strength workout exists, the dashboard continues to prioritize `Training fortsetzen`. An active native run similarly offers `Lauf fortsetzen`; starting a second simultaneous native session is not allowed.

## Running screen

The active screen is intentionally minimal and uses the existing LOCKED IN design system. It displays:

- large active running time;
- total distance in kilometres;
- smoothed current pace in minutes per kilometre;
- average pace in minutes per kilometre;
- positive elevation gain;
- a speaker button that toggles kilometre announcements;
- one pause/resume control;
- one stop control with confirmation before saving.

The timer and average pace use active time and exclude manually paused periods. Location samples may continue arriving while paused for diagnostic continuity, but they do not add distance, splits, pace, or elevation.

At each completed kilometre, an enabled audio coach announces the completed distance and the average pace. Speech uses the system German voice and briefly ducks other audio instead of stopping music playback.

## Tracking states

The running session follows an explicit state machine:

1. `preparing`: permission and usable GPS fix are being acquired.
2. `countdown`: three-second start countdown.
3. `recording`: accepted samples update distance and metrics.
4. `paused`: active duration and derived metrics stop advancing.
5. `finishing`: the user confirms stop and the final record is calculated.
6. `saved`: the run is persisted and all existing run views can read it.
7. `discarded`: an explicitly discarded run creates no `RunRecord`.

Only one native run or strength session can be active at a time.

## Tracking architecture

The tracking implementation is independent of SwiftUI and is split into testable responsibilities:

- `RunTrackingEngine`: owns `CLLocationManager`, session state, background recording, timers, and published live metrics.
- `RunLocationFilter`: classifies every incoming location as accepted or rejected and provides an exact rejection reason.
- `RunMetricsCalculator`: derives distance, rolling pace, average pace, splits, and filtered elevation from accepted active samples.
- `RunAudioCoach`: owns optional kilometre announcements.
- `RunLiveActivityManager`: starts, updates, polls controls from, and ends the running Live Activity.
- `RunSessionStore`: checkpoints the active session locally so reopening the app can restore its state when the process has not been force-terminated.

UI components consume an immutable live snapshot and do not calculate GPS metrics themselves. Filter and calculator settings are grouped into a versioned configuration so thresholds can change without rewriting UI or persistence.

## Initial GPS filtering

Every raw Core Location sample is retained for diagnostics, including rejected samples. Before a sample contributes to metrics, the filter validates:

- timestamp is not from the future and is no more than 10 seconds old when received;
- latitude and longitude are valid;
- `horizontalAccuracy` is positive and no greater than 25 metres;
- elapsed time since the previous accepted sample is positive;
- implied movement is plausible and does not represent a GPS jump;
- duplicate timestamp/location samples do not add distance.

The initial plausibility ceiling is deliberately generous enough for running and walking. Filter thresholds live in `RunTrackingConfiguration` and are included in diagnostic exports.

Distance is accumulated only between consecutive accepted, active samples. A rejected sample never becomes the origin of the next distance segment.

## Pace calculation

- Average pace is active duration divided by accepted distance.
- Current pace uses a rolling window of recent accepted movement instead of two individual GPS points.
- The initial rolling window targets roughly the most recent 30 seconds, with a minimum amount of movement before showing a value.
- Implausible or insufficient data displays `–:––` rather than a fabricated pace.
- Pace is stored internally as seconds per kilometre and formatted only in the presentation layer.

## Elevation calculation

Raw GPS altitude and vertical accuracy are retained. Metric elevation uses a separately smoothed series and ignores changes that fall inside a noise deadband. Positive and negative elevation are accumulated separately only from accepted active samples.

Core Motion relative-altitude data may refine this pipeline when available, but GPS-only recording must remain functional. The calculation API is isolated so comparison data can later drive different smoothing, deadband, or sensor-fusion versions.

## Splits

Each crossed whole kilometre produces a split containing:

- kilometre number;
- active duration for that kilometre;
- pace in seconds per kilometre;
- cumulative active duration;
- cumulative distance;
- positive and negative elevation for the split.

A partial final kilometre remains represented in the raw track and totals but is not announced as a completed kilometre.

## Persistence and data identity

Native runs use:

- `source = "lockedIn"`;
- their existing stable local `RunRecord.id` as identity;
- no Polar `externalId`.

Polar runs continue to use `source = "polar"` and deduplicate only by `source + externalId`. A native run and a Polar recording of the same real activity are never merged or deduplicated.

`RunRecord` gains optional, backward-compatible native fields for elevation totals, encoded route samples, encoded splits, algorithm version, and device/app diagnostic metadata. Existing manual and Polar rows remain readable without these values.

Each route sample contains at least:

- timestamp;
- latitude and longitude;
- altitude;
- horizontal and vertical accuracy;
- reported speed;
- cumulative accepted distance;
- accepted/rejected status;
- rejection reason;
- paused status.

The saved duration is active duration. Start time and total paused duration are retained so elapsed wall-clock time remains reconstructable.

## Background and lock-screen behavior

The app enables the location background mode and supplies clear location permission descriptions. Starting a run configures Core Location for fitness, best practical navigation accuracy, background updates, and the visible background-location indicator. Denial or restriction leaves the app usable and explains that recording cannot begin.

A dedicated running Live Activity is separate from the strength rest-timer activity. It displays:

- running time;
- distance;
- smoothed pace;
- paused/recording state;
- direct pause/resume control.

Stopping remains inside the app and requires confirmation to prevent accidental loss from the lock screen. The running engine polls the Live Activity control state so lock-screen pause/resume changes the actual metric accumulation, not only the displayed state.

Live Activity failure never ends or invalidates a running session.

## Export and backups

The existing backup payload is extended with all optional native-run fields while remaining able to decode older backups. Automatic backups continue after a native run is saved.

Settings gains a clearly labelled diagnostic training-data export for the comparison phase. It exports the complete training snapshot, route samples, rejected-point reasons, splits, algorithm version, filter configuration, app version, iOS version, and device model. The export contains no Polar access token, refresh token, client secret, or Cloudflare credential.

The raw-data export allows the same recorded route to be replayed through later metric algorithms without requiring the user to repeat the physical run.

## Error handling

- Permission denial prevents starting and shows a recoverable explanation.
- Temporary loss of GPS keeps the timer/session alive and displays unavailable live pace.
- Rejected samples are retained but never alter metrics.
- Failure to start or update a Live Activity does not affect tracking.
- Save failure keeps the finished session available for retry and does not silently discard samples.
- Audio failure disables only that announcement.
- Polar sync failure remains additive and does not affect native recording.

## Testing

Pure unit tests cover:

- stale, inaccurate, duplicate, and implausible sample rejection;
- accepted distance accumulation;
- paused samples adding no metrics;
- rolling and average pace;
- split creation across one or multiple kilometre boundaries;
- elevation deadband behavior;
- native versus Polar identity and non-deduplication;
- backward-compatible backup decoding;
- dashboard text changes.

Recorded deterministic location fixtures test the complete filter/calculator pipeline without requiring a live GPS device. Device verification additionally covers background recording, lock-screen Live Activity, pause/resume, audio announcements with music, and final persistence.

## Out of scope

- Heart-rate capture and AirPods/HealthKit association.
- In-app Polar-versus-LOCKED-IN comparison views.
- Route maps and interactive post-run charts.
- Social features, challenges, segments, friends, or records.
- Automatic merging of equivalent runs.
- Removing Polar or deleting its Cloudflare/Polar configuration; that happens only after the native mode has been validated and will require an explicit cleanup checklist.
